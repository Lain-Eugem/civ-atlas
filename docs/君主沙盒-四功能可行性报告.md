# 君主沙盒 · 四项功能可行性报告

> 日期：2026-11-11　范围：`mcp/viewer/`（监视台界面）+ `mcp/*.ts`（编排层）+ `src/gen/civ/`（纯计算）
> 结论先行：**四项都可行，且都不需要改推演引擎的事件堆**。全部落在「编排层 + 提示词 + 会话内状态」上，
> 关闭时引擎指纹与现在逐字节一致。真正的难点集中在功能三（角色卡 + Jev 审核）与功能四的情报部分。

## 2. 功能一 · 首次引导（两把 Key）

### 方案要点

1. **触发**：`app.js` 启动时读 `localStorage['civSandbox.onboarded']`；缺失且当前无会话 → 弹全屏浮层（复用 `.busy` / `.toast` 的玻璃卡视觉）。
2. **内容**：两段互相独立的卡片
   - 「LLM 扮演」：服务商下拉（DeepSeek / 百炼 / 自定义）+ baseUrl + model + Key，一个「测试连接」按钮；
   - 「Jev 判断」：Key（默认地址/模型折叠在高级里），一个「测试连通」按钮（走 `probe:true`）。
   - 底部：「稍后配置」（写 flag，直接进空地图）与「保存并开始」。
3. **提交路径**：不做新接口，直接复用到 `POST /api/monarch/setup`、`POST /api/petty/setup`（带 `probe:true`）。两者都已在 `viewer.ts:1039/1112` 存在，返回 `hasApiKey` 而不回显 Key。
4. **存储策略（需拍板）**：
   - A（推荐）**只存"已引导"标记与 provider/model**，Key 一律不落盘；进程重启后第一次跑回合时再问一次。
   - B 存 `localStorage`，刷新不丢，但 Key 会以明文进浏览器磁盘，与现有「Key 只在进程内存」的约定冲突。
   - C `sessionStorage`，关标签即丢，但浏览器仍可能落盘（崩溃恢复）。

### 难度：**低**

- 纯前端浮层 + 已有接口，无需改引擎、无需改 MCP 工具。
- 唯一需要新写的是「两段式校验状态」：分别记录 LLM/Jev 的 `connected | unconfigured | failed`，并让左侧行动栏在未配置时给出明确断点（否则用户点「跑一回合」只会看到一句 `先调用 civ_monarch_setup`）。

### 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| Key 落盘 | 与项目安全约定冲突；浏览器磁盘明文 | 默认 A 方案；B 必须显式勾选「记住（明文存在本机浏览器）」 |
| 引导把 mock 用户挡在门外 | 离线演示变麻烦 | 引导里保留「不用 Key，用 mock 演示」一键路径（`mock:true` 两条都开） |
| 自定义服务商 `response_format` 不支持 | 测试连接失败但实际可用 | 复用 `llm.ts:82` 已有的 400 回退逻辑；提示语写清「已按无 JSON 模式重试」 |
| 多标签页 / 进程重启 | 配置漂移 | 每次 `/api/state` 回来刷新 `hasApiKey`，界面以服务端为准，不以本地 flag 为准 |

## 3. 功能二 · 双开关（LLM 扮演 / Jev 判断）

### 方案要点

1. **建模**：在 `Session` 上加 `features: { llm: boolean; jev: boolean }`（默认由开会话时的参数决定），不再用 `mode` 兼表达。
2. **三条执行路径**（这正是三种组合）：

| LLM | Jev | 一回合做什么 | 入口 |
|---|---|---|---|
| 开 | 关 | `monarchRound`：简报 → LLM → 编译 → 一次 `playTurn` | `/api/monarch/round` |
| 关 | 开 | `pettyRound`：扫小事 → Jev → 抽签 → 落效果 → 一次 `playTurn`；国家行为交给引擎自动规则 | `/api/petty/round`（已有） |
| 开 | 开 | `monarchRound` 内部先 `settlePetty`，再合流（现状即如此） | `/api/monarch/round` |
| 关 | 关 | 纯 `turnStep`（"看海"模式，仍可推进历史） | `/api/turn`（已有） |

3. **后端改动**（小）：
   - `openSession` 接受 `features`，`mode` 仍保留为「本局是否允许 LLM 接管」的兼容字段；
   - `monarchRound` 在 `features.llm === false` 时明确报「本局未开 LLM 扮演」而不是「先调 civ_monarch_setup」；
   - `/api/state` 回传 `features`，前端据此灰掉按钮、切换底部标签（AI 决策 / 小事件裁决）。
4. **前端**：参数抽屉顶部放两个互斥无关的开关（`<input type=checkbox>` + 说明一行），保存到 `sessionStorage` 作为下次默认；关掉时对应子面板整体折叠。

### 难度：**低**（状态机细节为中）

- 引擎完全不用动；三个入口已经有实现，主要是"允许哪一个被调用"的路由与前置校验。
- 需要小心的是 `rounds` 计数：三种路径都会 `s.rounds += 1`（`turnStep` 内），所以自动播放、`maxRounds`、`finished` 天然一致，不用另建计数器。

### 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 「仅 Jev」时国家行为无人接管 | 用户以为 AI 在治国，其实是引擎规则 | 顶部状态条常驻显示「当前：引擎自动 + Jev 裁决」，AI 决策页写明"无君主" |
| 开关在会话中途切换 | 语义混乱（已跑 5 回合君主，第 6 回合改自动） | 开关只在「开会话前」可改；会话内只允许关闭（不允许重新打开），并在日志记一条 `features` 变更 |
| 仅 Jev 时 `s.monarch` 为空 | 现有 `verifySession` / `monarch.status` 面板会空 | 面板按 `features` 分支渲染，不假设 `s.monarch` 存在 |
| 双开时的顺序 | 小事先结算、君主后决策（现状）是正确的；反过来会让君主看到未结算的小事 | 顺序写进文档与自检断言 |

## 4. 功能三 · 君主角色卡（性格 / 偏好 / 自主记忆 / Jev 合理性审核）

这是四项里唯一需要新建"领域模型"的一项。

### 4.1 角色卡

**数据**：`MonarchCard`（纯数据，可导出、可手改）

```ts
{
  polityId: number,
  key: string,              // 稳定键，随国家走
  name: string,             // 君主名（引擎 rulerAt 给）
  born: number, title?: string,
  persona: string,          // 40–120 字：自然生物，不是国家意志
  traits: { caution: number, ambition: number, honor: number, greed: number }, // 0–100
  preferences: { war: 'avoid'|'opportunist'|'seek', economy: ..., diplomacy: ... },
  competence: { war: 0|1|2, economy: 0|1|2, intrigue: 0|1|2, admin: 0|1|2 },  // 决定"能想到什么"
  createdAt: number, fromRulerBorn: number,
}
```

- **性格从哪来**：引擎已有 `ruler.leanings`（expand/war/develop/trade），先做确定性映射，再由 LLM **只润色 persona 文本**（不改数值），失败就用模板。这样同一世界 + 同一君主永远得到同一张卡。
- **"自然生物"怎么落地**：persona 里必须包含三件事——①有寿命（会说"我今年四十七，等不了二十年"）；②信息有限（只知道简报里的东西）；③有情绪与偏见（记仇、怕死、好面子）。同时 system prompt 加一条硬约束：**不得以"国家利益最大化"口吻做超越个人的决策**。
- **生命周期**：君主死亡 / 改朝换代（`rulerAt` 换人）→ 卡重建，旧记忆归档进 `history`，新君带"先王遗命"一条。这是必须处理的，否则"角色卡"会和引擎的君主更替脱节。

### 4.2 独立记忆库

**存储**：`Session.monarch.memory[polityId] = { entries: [...], revision: number }`，落盘到 `mcp/.runs/<sid>/monarch-memory.json`。

```ts
{ year: 2510, kind: 'war'|'loss'|'betray'|'gift'|'self', text: 'P6 在 2508 年背盟，此仇必报', weight: 0.8 }
```

- **写入者有两种**：
  1. **引擎事实**（自动，确定性）：本国战败、丢都、饥荒、被背盟 → 由 annals 派生一条，权重高；
  2. **君主自述**（LLM 自主写入）：决策 JSON 增字段 `remember: [{text, weight}]`，每回合 ≤2 条、每条 ≤60 字，总数上限 16，满了按权重+新旧淘汰。
- **只进提示词，不进引擎**：记忆不产生命令、不改数值。引擎确定性因此完全不受影响；LLM 的不可复现只体现在"下了什么命令"，与现有口径一致。
- **审核联动**：Jev 审核时可以顺带判断"这条记忆是否与事实矛盾"（可选，建议 v2 再做，避免一回合两次额外调用）。

### 4.3 每回合的 Jev 合理性审核

**这是功能三的核心，也是最容易设计错的地方。**

- Jev 只能回答概率，所以"禁止"必须变成**可判定阈值**，不能指望模型直接说"不许"：
  - 一次请求里按 `audit.p{polityId}.o{index}` 批量问，全部用 `choice`：
    `{ fit: '符合该君主身份与能力', stretch: '勉强，但可以解释', beyond: '超出其判断能力/性格' }`
  - 判决规则（确定性）：`p(fit) ≥ 0.55` → 放行；`p(beyond) ≥ 0.35` 或 `p(fit) < 0.35` → 退回；其余 → 降级（见下）。
  - 阈值全部进配置、写进日志，便于调参与复现。
- **三层护栏，顺序不能反**：
  1. 引擎硬校验（`compileMonarchOrders` 已有的接壤/在世/参数校验）——**永远第一**；
  2. 角色卡能力校验（纯规则，便宜）：`competence.intrigue = 0` 的君主不能下"渗透"；`preference.war = 'avoid'` 且 `caution > 70` 时，宣战需要 Jev 更高把握；
  3. Jev 合理性审核（软约束，可能失败/超时）——只做"降级"与"退回"，不做硬拒。
- **降级而不是丢弃**：`beyond` 的命令不直接删，改成更保守的等价命令（宣战 → `policy:hold`；结盟 → 空；`press` → `halt`），并把原文写进 `decisions[].audit`。这样界面上能看到"他想打，但被判断为不像他会做的事"。
- **失败降级**：Jev 不可达 → 该回合**只走第 2 层规则校验**，日志标 `audit: 'skipped'`，绝不阻塞回合（与 petty 的降级策略一致）。
- **成本控制**：所有君主的所有命令合并成**一次** Jev 请求（`questions` 上限 64，8 国 × 3 条 = 24，够用）；和 petty 的小事问题、渗透问题可以合并在同一批，受 4250 token 预算约束。

### 难度：**高**

理由：

1. **新增三份跨回合状态**（卡、记忆、审核历史），都要落盘、都要进导出、都要考虑"换了君主怎么办"。
2. **"合理性"没有客观真值**：Jev 给的是概率，必须自己定义阈值与降级映射；定义错了会变成"AI 什么都不许做"或"审核形同虚设"，需要拿真实对局调参。
3. **每回合多一次网络调用**，且与现有 `Promise.all` 的并发结构、失败重试、120s 回合预算相互影响。
4. **提示词体积上涨**：卡 + 记忆 + 审核理由会让每国上下文从 ~1.2k 涨到 ~2k tokens，直接抬高成本与延迟。
5. **一致性陷阱**：记忆是模型写的自然语言，可能与引擎事实冲突（"我灭了 P6"但 P6 还活着）。必须每回合用引擎事实做一次冲突消解（活着/死亡/战争状态），否则模型会基于幻觉决策。

### 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 审核把玩法锁死 | 君主永远只敢守成 | 阈值可配；先只审"高影响命令"（declare/press/destroy），政策类默认放行 |
| 记忆膨胀 / 幻觉累积 | token 爆、决策跑偏 | 上限 16 条 + 权重淘汰；每回合与 annals 对齐，矛盾条目自动降权 |
| Jev 只看文本，不懂引擎语义 | 审核结论与实际可行性脱节 | 审核问题里附结构化事实（州数、邻国、国力比），且引擎硬校验永远先跑 |
| 卡与君主更替不同步 | 死人还在发命令 | 每回合开始用 `rulerAt` 校验；换了人就重建卡、归档记忆 |
| 成本翻倍 | 12 国 × 12 回合的账单 | 批量一次请求；只在开 LLM 时审；`mock` 走确定性替代（按 traits 打分） |

## 5. 功能四 · 提示词工程（分层 / 缓存 / 逐州属性 / 情报）

### 5.1 分层与前缀缓存

**现状问题**：`buildMonarchBriefs` 生成的文本第一行就是 `你是…现在是第 2510 年。`（`monarch.ts:180`）。年份一变，整段前缀全变，**任何前缀缓存都不可能命中**。同时 system prompt 只有 19 行，几乎没有可复用的稳定内容。

**目标结构**（从稳定到易变，逐字节稳定优先）：

| 层 | 内容 | 变化频率 | 预估 tokens |
|---|---|---|---|
| L0 system | 身份框架、输出契约、命令说明、"你是自然生物"硬约束 | 全局固定 | ~600 |
| L1 角色卡 | persona / traits / preferences / competence | 换君主才变 | ~250 |
| L2 世界常量 | 纪元、地图规模、规则说明（税率口径、稳定度定义） | 全局固定 | ~200 |
| L3 记忆库 | 按权重排序的 ≤16 条 | 缓慢 | ~200 |
| L4 长周期局势 | 天下国家列表（按大小）、地理邻接 | 每回合微变 | ~300 |
| L5 本年局势 | 年份、本国州数/国都/君主、战争、最近大事 | 每回合变 | ~400 |
| L6 逐州表 | 本国 top-N 州 + 汇总 | 每回合变 | ~500 |
| L7 情报 | 他国已知/陈旧/未知 | 每回合变 | ~200 |

- 关键动作：**把年份从第一行挪到 L5**；把「命令契约」「输出格式」从每份简报里移出，放进 L0/L2 只出现一次。
- 消息结构：`system` = L0 + L1 + L2（长期不变），`user` = L3…L7。多数 OpenAI 兼容服务商按"前缀逐字节一致"命中缓存；同一进程内同一国家的 system 段可跨回合完全一致。
- **可测**：在回复里读 `usage.prompt_cache_hit_tokens`（DeepSeek 口径）或等价的 cached tokens 字段，写进回合日志；`civ_monarch_status` 增加 `cacheHitRate`。没有这个数就没法证明分层有效。

### 5.2 逐州属性表

引擎里能拿到的真值（已核实）：

| 想要 | 引擎真值 | 函数/字段 | 结论 |
|---|---|---|---|
| 人口 | ✅ 逐州（乡村 + 城市） | `regionPopulationAt(civ, r, year)`（`growth.ts:424`） | 直接可用 |
| 粮食产量 | ✅ 可代理：乡村容量 / 宜居度 | `ruralCapacity(regions, r)`、`regionSuitability`（`growth.ts:319-325`）；物产表 `RESOURCES` 含"粮"（`development.ts:83`） | 用容量×开发度做"产粮能力"，标注为估算 |
| 税收 | ⚠️ **只有国家账本**（田赋/工商/市税…） | `fiscalBook.ts:18` 的 `BOOK_COLS`，`fiscalAt(civ, p, year)` | 逐州只能按人口/开发度**分摊**，必须标"分摊估算" |
| 稳定值 | ❌ 无逐州真值 | 可组合：`controlAt(civ,year)[r]`（4 档，`control.ts:166,189`）+ 近期折损/饥荒（annals） | 定义「稳定度 = 控制档位 × 战乱折损 × 饥荒」0–100，标注为推算 |
| 开发/能力 | ✅ 逐州五能力快照 | `development.snaps` + `CAPS`（`inventions.ts:8`：生产/运输/信息/行政/动员） | 直接可用 |

**表格规模控制**：34k 地块世界约几百州，全表塞进提示词不现实。方案：按人口取 **top 8–12 州**逐行列出，其余按「其余 N 州：人口合计、税收合计、稳定均值」汇总；并在 system 里说明口径。

**新模块**：`src/gen/civ/monarchIntel.ts`（纯计算，可单测）导出 `regionRows(civ, polityId, year, opts)`。所有"推算"字段在返回结构里带 `derived: true`，UI 与提示词都显式写"估算"，避免把估算当引擎事实。

### 5.3 情报机制（渗透）

**关键判断：不要做成引擎命令。** 渗透不改变历史，只改变"君主知道什么"，属于会话层状态；做成 `Intervention` 会污染命令史、影响回放口径，收益为零。

**设计**：

1. **行动通道**：君主决策 JSON 增加 `actions: [{kind:'intel', b: 6, focus:'tax'|'pop'|'stability'}]`，在 `compileMonarchOrders` **之前**被摘走，交给 `mcp/intel.ts`；`commands` 仍走原路。
2. **判定**：每回合把 N 条渗透合并进同一次 Jev 请求（`choice`）：
   `{ none:'一无所获', partial:'拿到人口与稳定，没拿到税收', full:'三项都拿到', blown:'被对方发觉' }`
   `blown` 只影响叙事与下次成功率（会话层衰减），不产生引擎命令。
3. **抽样**：用 Jev 概率 + 引擎同款确定性抽签（`src/gen/civ/petty.ts` 的 `pickByWeight`，种子 `intel:<year>:<a>:<b>`），结果进日志。
4. **状态**：`intel[myPolity][targetPolity] = { year, fields: ['pop','stability'], quality }`；提示词里他国数据按此**字段级遮蔽**：
   - 未侦察 → `人口：未知`；
   - 已侦察但 >10 年 → `人口：约 120 万（第 2500 年）`；
   - `blown` → 冷却 5 年不可再探。
5. **成本**：每条渗透 1 个 Jev 问题，与审核、小事共用一次请求、共用 4250 token 预算；超预算按 P2 丢弃（与 petty 的降级策略一致）。

### 难度：**中**（4a/4b）、**中-高**（4c）

- 4a：改动集中在一个函数（`buildMonarchBriefs`）+ `prompt.ts`，但要保证"稳定段逐字节一致"，容易被一个随年份变化的字符串破功；收益需要真实用量证明。
- 4b：人口/能力有真值，**税收与稳定只能推算**——这是产品口径问题而不是技术问题，必须显式标注，否则用户会把它当引擎事实。
- 4c：新增"君主行动"这一层概念，要和命令编译、Jev 批量、预算、日志、UI 五处对齐；且"知道/不知道"是新的状态机，容易漏掉陈旧度与冷却。

### 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 分层没命中缓存 | 白改，token 反而涨 | 用 `usage` 里的 cached tokens 做验收；L0–L2 内禁止出现年份/随机 id |
| 逐州表太长 | 超出上下文或挤掉编年史 | top-N + 汇总；`regionRows` 带 `maxRows` 参数 |
| 税收分摊被当真实数据 | 用户误判国力 | 字段带 `derived:true`，UI 加"估"角标，提示词注明"分摊估算" |
| 情报变成"上帝视角" | 君主全知，失去策略张力 | 字段级遮蔽 + 陈旧度 + 冷却；未侦察国只给"州数区间" |
| Jev 判决不可复现 | 同一局两次跑结果不同 | 概率落盘 + 确定性抽签；回放仍按命令史核对（引擎侧不受影响） |

## 6. 交叉风险

| 类别 | 说明 | 对策 |
|---|---|---|
| **确定性口径** | 四项都只影响"下什么命令"，不影响"同一串命令推出什么"。开任意功能后 `civ_session_verify` 仍应 `ok:true` | 每项都加一条自检：关功能 = 官方指纹；开功能 = 回放一致 |
| **安全** | viewer 只监听 `127.0.0.1`，但 `/api/*` 无鉴权；一旦 Key 落盘，风险从"内存"升级为"磁盘" | 默认不落盘；任何持久化都要显式勾选 + 文案 |
| **构建/部署** | `mcp/` 是 tsc 产物，服务端代码改了必须重启 viewer 进程（前端 `app.js` 是静态文件，刷新即可） | 文档与 toast 明确提示；`sandboxViewer.ts` 已有"比源码旧就重建"的逻辑 |
| **成本** | 双开 + 审核 + 渗透 = 每回合 1 次君主调用/国 + 1 次 Jev；12 国 12 回合约 150 次调用 | 批量 Jev、预算闸门、`civ_monarch_status` 显示本局累计 usage |
| **兼容** | 新增字段全部可选，缺省 = 现有行为；`session.json` 与导出格式加版本号 | 旧会话读回按"无卡/无记忆/无情报"处理 |

## 8. 需要你拍板的三个决定

1. **Key 是否落盘**：默认不落盘（每次启动重填），还是勾选后存 `localStorage`？
2. **Jev 审核的强度**：只审高影响命令（宣战/坚持打/灭国），还是全部命令都审？（前者便宜且不容易锁死玩法）
3. **渗透的位置**：确认走「会话层行动」（推荐，不碰引擎），还是希望它也进命令史（可回放但会污染引擎语义）？
